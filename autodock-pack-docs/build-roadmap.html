How to read this plan

Three tracks, run mostly back-to-back with one deliberate overlap:

  • Track A — everything you can build and test today on the Mac M4: recognition logic, SKU onboarding, the lookalike-rice model, the checkout flow. This proves the software is correct.
  • Track B — the same pipeline ported onto an actual RK3588 board. This proves the numbers are real, since M4 latency does not predict RK3588 latency. It ends in a go/no-go gate before you commit to a custom board.
  • Track C — the production device: carrier board, packing mechanics, certification, cloud backend, and the live pilot.

Track B starts in week 3, once Track A has something worth porting — you don't wait for Track A to fully finish.

02

Track A Local M4 prototype

Goal: prove the logic is correct — recognition, onboarding, promotions, offline resilience — using the Mac M4 as a stand-in compute box. None of the latency numbers from this track are final; they're a baseline to compare against Track B.

A0 · Environment setup

Day 1–2
  1. Create the ARM64 conda environment and install MLX, PyTorch+MPS, FAISS-CPU, OpenCV, transformers, mlx-vlm — this is the same stack your blueprint already scripted.
  2. Load Qwen2-VL-2B (4-bit) via mlx-vlm once, just to confirm the model loads and generates on the M4's unified memory.

A1 · Bridge real sensors into the M4

Day 2–4
  1. Wire a TI ADS1232 breakout + load cell to a spare ESP32stream weight readings to the Mac over USB-serial (pyserial) — testing against real sensor noise beats testing against a hand-typed number every time.
  2. Get one or two USB UVC cameras (or a capture card feeding the actual M12 lens modules)the M4 has no MIPI-CSI input, so this is the stand-in for the dual Sony IMX415/OV5647 cameras until the carrier board exists.

A2 · Core recognition pipeline

Week 1–2
  1. Weight-gate triggerfire only on ΔW > 15g from the live serial stream.
  2. Weight pre-filternarrow your local SKU catalog (JSON) to items within tolerance of the measured weight.
  3. Fast patha lightweight pretrained embedding model (MobileNetV3/V4 via PyTorch+MPS) turns the live camera frame into a vector, matched against a local FAISS index.
  4. Deep pathQwen2-VL fallback when the fast path isn't confident.
  5. Log everythingwhich path fired, confidence, per-stage timing — into a local SQLite table. This becomes your Track A benchmark report.

A3 · SKU onboarding tool

Week 2
  1. Build a small capture script4 photos + weight per SKU → embedding → append to the local FAISS index + catalog metadata.
  2. Onboard 15–20 test SKUsmix packaged snacks, dals, and all four rice types — you need a realistic catalog before the next phase means anything.

A4 · Lookalike-rice model

Week 3–4
  1. Capture 50–100 labeled photos per rice varietyBasmati, Sona Masoori, plain rice, idli rice — vary fill level, angle, lighting.
  2. Add the density featureweight ÷ estimated tray-fill volume, computed alongside the image.
  3. Baseline testrun the off-the-shelf embedding + density fusion, build a confusion matrix across the four varieties.
  4. Fine-tune if the baseline is weakcontrastive/triplet fine-tuning on the captured set, still on the M4 via PyTorch+MPS. Target: >95% top-1 accuracy among the four varieties before moving on.

A5 · Checkout flow + promotions simulation

Week 4
  1. Minimal local web UIweigh → identify (show candidate + confidence) → apply a promotions JSON rule file → mock payment → print a "pack" signal.
  2. Exercise discount and free-item rules% off, buy-X-get-Y, ₹0 loyalty override — against the same rule format planned for production.

A6 · Offline resilience + benchmark writeup

Week 5
  1. Local outbox table for transactionsplus a mock "cloud" endpoint (can be a script on your own machine) to prove the sync pattern.
  2. Kill the mock endpoint mid-testconfirm the queue holds and drains correctly once it's back.
  3. Write the Track A reportaccuracy numbers, model sizes, tuned confidence thresholds. This is what hands off to Track B — not the M4 latency numbers themselves.
03

Track B Real-hardware validation gate

This track exists because an M4 has roughly 5–6x the RK3588's NPU throughput. Nothing you measured in Track A tells you whether the real device will hit <350ms — only the real chip does.

B1 · Get a real board

Week 3–4, parallel with A4
  1. Order an Orange Pi 5 Plus or Radxa Rock 5BRK3588, 8GB+ RAM — roughly $100–150, and the fastest way to get real numbers without waiting on the custom carrier board.
  2. Install RKNN-Toolkit2set up the quantization/conversion environment on a dev machine.

B2 · Port the models

Week 5–6
  1. Convert the fast-path embedding model to INT8 via RKNN-Toolkit2budget 1–3 engineer-days for calibration and accuracy validation.
  2. Convert the VLM to INT4 via the RKLLM toolkitthis is the least-proven step in the whole plan — start it early, expect iteration.
  3. Re-run the identical test set from Track Asame photos, same weights, same rice-variety dataset — so the comparison is apples-to-apples.

B3 · Real latency + thermal test

Week 6
  1. Measure per-stage latency on the RK3588 boardfast path, deep path, end-to-end — against the <30ms / ~250ms / <350ms targets.
  2. Run a sustained load teste.g. 500 back-to-back checkouts inside a sealed test box, not an open dev board — this is what actually reveals thermal throttling.

B4 · Go / no-go decision

End of Week 6 Gate
  1. Golatency and thermal numbers hold up → lock RK3588S, start the custom carrier board (Track C).
  2. No-goif quantization can't close the gap, this is the one point in the plan where reopening the RK3588-vs-Jetson decision is worth the cost — not before.
04

Track C Production build & pilot

C1 · Carrier board + packing mechanics

Week 7–9
  1. Finalize the custom carrier boardroutes dual MIPI-CSI (cameras), eDP (touch panel), RS-485 (ADS1232 weight ADC), and a UART/CAN handoff to the packing MCU.
  2. Confirm the camera modulesSony IMX415/OV5647 with M12 fixed-barrel lenses and bonded polarizers, per the blueprint.
  3. Put packing on its own MCUa second ESP32 (or STM32) drives the drop + seal actuators for the 20kg chute — kept off the RK3588 so a burst of AI inference never makes the packing arm stutter, and vice versa.
  4. Resize the chassisCRCA steel, IP52, now sized for compute + packing mechanism together, with passive airflow paths so the RK3588 stays fanless.
  5. Size the power supplyconfirm the MeanWell 12V/5A budget still covers compute + cameras + touch panel + packing actuators, or step up if the motors draw more.

C2 · BOM & manufacturing partner

Week 7–9, parallel
  1. Get the packing subsystem quotedmotors, actuators, chute, sealing consumables — this is the piece missing from the blueprint's ₹32.8–38.5K checkout-only BOM.
  2. Engage a prototype/manufacturing partnerthe same way Smart Soak used Inceptarc — either that vendor pool or one that specializes in kiosk-class hardware.
  3. Reconcile the target BOMtoward the deck's ₹98.5K batch figure once packing is quoted for real.

C3 · Certification

Week 9–11, parallel
  1. Legal Metrology certificationrequired — the device bills customers by weight.
  2. BIS & WPC approvalsas already scoped in the blueprint.

C4 · Cloud & fleet software

Week 7–10, parallel
  1. Stand up the brand/branch/kiosk hierarchy backendmaster catalog in Qdrant, MQTT broker, analytics store, promotions engine.
  2. Build the admin dashboardSKU onboarding, branch config, promotions, daily checkout analytics per device.
  3. Build the OTA pipelineversioned model/software updates with rollback.

C5 · Bengaluru pilot

Week 10–12
  1. Install the pilot unit(s)first real store deployment.
  2. Run to the 1,000-checkout targetthe milestone that matters more than a polished machine.
  3. Watch five things closelyrecognition accuracy on lookalikes, real-world latency, thermal behavior over a full day, payment reliability, and packing mechanism safety.
  4. Feed pilot data backinto the lookalike model and the final BOM before scaling to a second branch.

Open items to close before you commit hardware spend

UnquotedPacking subsystem cost (motors, actuators, chute, sealing consumables) — nothing in either source document prices this out yet.
UnvalidatedEvery latency number in this plan (<30ms / ~250ms / <350ms) is a target until Track B, Phase B3 produces real RK3588 numbers under thermal load.
UnconfirmedManufacturing partner for the kiosk hardware — Inceptarc is your Smart Soak vendor; decide whether they (or someone new) build this too.
Worth deciding earlyWhether customers load items one at a time or in a mixed batch — that answer changes whether the fast path needs object detection (YOLO-class) or can stay a single-item classifier, per the earlier tech-stack discussion.
